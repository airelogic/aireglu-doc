Permission Gating ​

Permission gating is an optional extension of Open ID Connect Bearer Token authentication. As well as checking that the caller's token is valid, AireGlu checks that the user behind the token holds specific permissions before the endpoint runs.

Use it when:

  • Only some users of an application should be able to call an endpoint (for example, only users who can edit:widget should be able to update a widget)
  • The endpoint is exposed as an MCP tool or resource and should only be visible to users who are allowed to use it
  • Permissions are already managed centrally in AireIdentity and you don't want to repeat them in endpoint logic

How it works ​

Permission gating runs as part of authentication, after the token has been validated:

  1. The caller sends a user access token (Bearer header or form POST, see How callers pass a token).
  2. AireGlu validates the token's signature, issuer, expiry, audience and scopes as normal.
  3. AireGlu asks the permission source which permissions the user holds in each configured Target Scope, using the caller's own token.
  4. The caller must hold every listed permission in every gated Target Scope. If anything is missing, authentication fails.
  5. On success the endpoint runs, and the caller's token is available via liquid within the AireGlu Tasks request.userToken.

Why it works this way ​

  • The user's own token is used for the lookup. AireIdentity only returns permissions for the user the token belongs to. A caller cannot ask about anyone else's permissions, and AireGlu doesn't need a privileged service account to read them.
  • The check is live on every request. Lookups are not cached, so revoking a role or policy in AireIdentity takes effect on the next call. There is no window where a removed user can keep calling the endpoint.
  • It fails closed. If the permission source is unreachable, returns an error or returns nothing, the request is rejected. An outage never silently grants access.
  • It lives on the endpoint, not on whatever calls it. The same gate applies whether the endpoint is called over HTTP, from an iframe or as an MCP tool. You configure it once.

Configuring permission gating ​

In the endpoint editor, open Authentication and add (or edit) an Open ID Connect Bearer Token method. Configure Authority, Audiences and optional Scopes as described in Configuring an endpoint, then:

  1. Under Permission gating, tick Fetch and validate permissions for Target Scope(s).
  2. Choose a Permission source:
    • AireIdentity (default): permissions are read live from AireIdentity's policy service.
    • Custom Endpoint: see Custom permission source.
  3. For each Target Scope:
    • Enter the Target Scope, the scope of the target application in AireIdentity's policy service (for example PatientRecordsApi).
    • Add the Permissions the caller must hold in that scope, in action:resource format (for example read:patient). Type each permission and press Enter.
  4. Click Add Target Scope to gate on further scopes.
  5. Save the endpoint.

Target Scope vs Scopes ​

The Scopes field and Target Scope look similar but answer different questions:

ScopesTarget Scope
ChecksThe scope claim inside the tokenThe user's permissions in AireIdentity's policy service
Answers"Was this token issued for this kind of call?""Is this user allowed to do this?"
ExampleAireGluRuntimeApiPatientRecordsApi

The Target Scope is usually the scope of the application the endpoint acts for, which is often not a scope the caller's token carries.

Matching rules ​

  • All Target Scopes must pass, and within each one the user must hold all listed permissions (AND, not OR). To allow "either A or B", create separate endpoints or use a custom permission source.
  • Scope and permission names are compared case-insensitively.
  • A Target Scope with no permissions doesn't trigger a lookup. It still appears in authentication.targetScopes, which is useful for passing a scope to a Delegate Exchange connection without gating on it.
  • Only one Open ID Connect Bearer Token method per endpoint version can have Target Scopes.
  • If the endpoint has other authentication methods, all of them must still pass.

Requirements ​

  • The Authority must be your AireIdentity instance when using the AireIdentity permission source. Lookups always go to the AireIdentity instance AireGlu itself is configured with, so tokens from third-party identity providers can't be gated this way.
  • Users get permissions through roles and policies in AireIdentity. A user with no role granting the permission is rejected.

What the caller sees ​

SituationResult
Token valid, all permissions heldEndpoint runs
Token valid, a permission missing401 Unauthorized
Permission source unavailable or errors401 Unauthorized (fail closed)
Called as an MCP tool or resourceSee MCP Permissions: the tool is hidden from the user rather than returning 401

Rejected requests are recorded as an authentication failure in the endpoint's usage data.

Using target scopes in Liquid ​

The configured Target Scope names are available in task templates as authentication.targetScopes:

liquid
{{ authentication.targetScopes[0] }}
{{ authentication.targetScopes | join: ' ' }}

This contains the configured scope names (after variables are resolved), not the permissions the user holds. Its main use is to keep the scope you gate on and the scope you request downstream in step. For example, use it as the scope parameter of a Delegate Exchange connection.

authentication.targetScopes is empty in Preview.

Permission gating and downstream calls ​

Permission gating decides whether the endpoint runs. It doesn't change the credentials the endpoint's tasks use when they call other systems.

If a task calls a downstream API as the user, use a Delegate Exchange connection. It swaps request.userToken for a token scoped to the downstream API. The downstream API should still enforce its own data-level access (for example, which patient records this user may see). Permission gating is the first check, not the only one.

A typical layered setup:

LayerQuestionEnforced by
EndpointCan this user call this endpoint at all?Permission gating
Downstream credentialWhat may AireGlu do on this user's behalf?Delegate Exchange connection, Target Scope on the exchanged token
DataWhich records can this user see?The downstream API

Best practices ​

  • Gate on the action, not the user. Grant permissions through roles and policies in AireIdentity rather than per-user, so access is managed in one place.
  • Keep permission sets small and specific. Required permissions are ANDed, so each one you add narrows who can call the endpoint.
  • Use one Target Scope per application. Add a second Target Scope only when the endpoint genuinely acts on two applications (for example records and billing).
  • Don't treat gating as data security. Keep record-level checks in the downstream system, and pass the user's identity to it with a Delegate Exchange connection.
  • Expect a lookup per request. Each gated call makes a live request to AireIdentity. For high-volume, non-user traffic, use Client Credentials on a separate endpoint instead.
  • Test with a user who lacks the permission. Confirm they get 401 (or don't see the MCP tool) before going live.
